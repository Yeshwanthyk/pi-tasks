Pi Tasks Lifecycle: Current States And Expected Next Shape

A source-cited view of how Task Status, Task Execution, Blockers, Auto-Cascade, Auto-Clear, and the proposed Subagent Adapter relate today.

What is happening now

One Task has two lifecycles

The stored Task Status is compact: pending, in_progress, completed. Subagent-backed work adds a second persisted Task Execution state: running, completed, failed, stopping, or stopped. The confusing cases come from translating between those two lifecycles.

Architectural pressure

Protocol behavior lives in the entrypoint

The pi RPC request/reply protocol, subagent version detection, spawn/stop calls, event subscription, widget updates, and Task Execution dependencies are wired together in the extension entrypoint. That makes the Subagent Adapter the highest-leverage next Module.

Current composition flow

Task Store

Source of truth for Task List, Task Status, Blockers, Owner, and execution payload.

Tool Handlers

TaskCreate, TaskUpdate, TaskClaim, TaskExecute, TaskOutput, TaskStop.

pi Events/RPC

Ping, spawn, stop, completed, failed, and notification delivery.

Task Execution

Launches agents, maps agent IDs to Tasks, writes results, and cascades.

Widget/Reads

TaskList, TaskGet, output, active spinner, Auto-Clear, reminders.

Invariant

Blocked work cannot start

TaskClaim and TaskExecution both treat missing or non-completed Blockers as open.

Invariant

Failed execution is retryable

A failed subagent sets Task Status back to pending while preserving failure metadata in Task Execution.

Invariant

Stopped means completed

Intentional stop is represented as Task Status completed with Task Execution stopped.

Stored Task Status

pending

Created or retryable. May be blocked by open Blockers.

→

in_progress

Manual active work or running Subagent Task.

→

completed

Resolved, stopped, or shell-stop treated as done.

There is also a delete command path, but deletion is not a stored Task Status: `status: "deleted"` removes the Task from the store.

Expected next Module

Subagent Adapter

Place a seam between pi event protocol details and Task Execution. The Adapter owns version detection, RPC envelopes, timeouts, spawn/stop, and subscriptions. Task Execution keeps the domain lifecycle.

Current coupling: src/index.ts:137-184
Deletion test

Why this Module is deep enough

If the Adapter is deleted, protocol complexity reappears in TaskExecute, TaskExecution tests, availability checks, stop handling, and event listeners. That means the Module would buy real locality.

Recommended Interface shape to explore

Result-based availability: TaskExecute calls TaskExecution; TaskExecution calls the Adapter; Adapter methods return domain-friendly results instead of leaking `subagentsAvailable`, ping replies, or channel names. That keeps the caller from learning protocol ordering.
